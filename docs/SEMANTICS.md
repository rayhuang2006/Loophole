# 操作語義

這份文件精確定義 `wishc` 執行一個願望時到底發生什麼。

它是整個專案唯一的嚴謹來源。Loophole 不做任何全稱證明——它不宣稱「精靈永遠攻不破」，
也不需要。它宣稱的只有一件事：**給定一支具體的願望程式，它是否合規、是否拆穿了精靈的本意，
是一個有確定答案的問題**，而這份文件就是那個答案的定義。

所以這裡每釘死一條，exploit 就多一分是「推論」而不是「巧合」。反過來說，
這裡沒寫清楚的地方，都是嘴砲能鑽進來的地方。

---

## 世界狀態

世界有四個部分：

| 部分 | 可不可以被願望改 | 說明 |
| --- | --- | --- |
| 暫存器 | 值和位寬都可以 | `register wishes : uint<2> = 3` |
| 人 | **不行** | `people alice, bob` 宣告後就固定，這是接地的事實 |
| `alive` 位元 | 可以（`kill` / `revive`） | 接地狀態 |
| 定義 | 可以（`define`） | 可重綁的名字，見下面 |
| 承諾 | 只能增加（`promise`） | 精靈給出去的話，收不回來 |

「人的名單不可改、定義可改」這個區分是 Phase 2 全部的重點。
不變量寫在名單上就守得住，寫在定義上就守不住。

### 暫存器

每個暫存器有兩個欄位：

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `val` | 64-bit 無號整數 | 目前的值 |
| `width` | 整數 1..64 | 這個暫存器的位寬 |

一個暫存器的**遮罩**定義為

```
mask(w) = 2^w - 1        （w < 64）
mask(64) = 2^64 - 1
```

不變條件：任何時刻都有 `val = val AND mask(width)`。也就是 `val` 永遠是已經截斷過的，
不存在「位寬外面還藏著位元」這種事。位寬變窄時被切掉的位元是**真的沒了**，不會在變寬時回來。

宣告語法：

```wish
register wishes : uint<2> = 3
```

位寬在 parse 階段就限制在 1..64；超出範圍是編譯錯誤，不是 exploit。
初始值會先經過一次截斷，所以 `register r : uint<2> = 7` 得到的是 3。

## 指令

五個操作，加上兩個不是操作的語句（`define` 和 `promise`）。
操作全部精確定義成一次狀態變更。

### `sub r, k`

```
r.val := (r.val - k) mod 2^r.width
```

**沒有下限檢查。** 減到負的就繞回去。這條就是笑話 #1 的全部。

### `add r, k`

```
r.val := (r.val + k) mod 2^r.width
```

沒有上限檢查，一樣繞。不過在 v0 的世界裡對 `wishes` 用 `add` 會先被規則 R1 擋下，
所以這條實際上沒什麼用（見下面 R1）。

### `widen r -> uint<w>`

```
r.width := w
r.val   := r.val AND mask(w)
```

名字叫 widen，但**沒有任何地方檢查 `w` 比原本的位寬大**。所以：

- `w` 比較大：值不變（高位補 0），這是笑話 #2 走的路。
- `w` 比較小：值被截斷，高位真的丟掉。

這是搜尋器找到、我沒設計的那個洞。要不要把它改成只准變寬，是個設計選擇而不是 bug 修復——
留著它，「要一個更小的架子」就是一種合法招式；擋掉它，`widen` 就名副其實。
目前的決定是**留著**。

### `kill p` / `revive p`

```
alive[p] := 0        （kill）
alive[p] := 1        （revive）
```

`p` 必須是 `people` 宣告過的人，否則是執行期錯誤。這兩個是**接地操作**：
它們動的是真實狀態，不是任何標籤。無論你把它們叫成什麼名字，效果都一樣。

### `promise <命題>`

不動世界。它把一條**承諾**加進精靈的帳上，然後精靈的兩條元公理就開始適用：

```
A1   精靈實現每一個合規的願望
A2   精靈信守它做出的每一個承諾
```

這兩條不是檢查表上的項目，是精靈對自己的描述。實現一個合規的願望 `w` 時，帳上加兩筆：

```
A1：  granted(w)
A2：  granted(w) implies <承諾的內容>        每個 promise 各一筆
```

命題的文法（全 ASCII，結合力由鬆到緊）：

```
formula := disj [ "implies" formula ]        右結合
disj    := conj { "or" conj }
conj    := unary { "and" unary }
unary   := "not" unary | atom
atom    := "granted" "(" 願望名 ")" | "alive" "(" 人名 ")"
         | "true" | "false" | "(" formula ")"
```

兩種原子的地位**完全不同**，這是這條軸的關鍵：

| 原子 | 是什麼 | 誰決定 |
| --- | --- | --- |
| `granted(w)` | 自由變數，每個願望一個 | 精靈。它可以選要不要實現 |
| `alive(p)` | **常數**，不是變數 | 世界。命令式引擎先跑完，這個值就定了 |

`granted(self)` 裡的 `self` 指做出這個承諾的願望。它在解析之後才被代換成願望名字，
所以一個願望可以談論自己被不被實現，而語言不需要知道它叫什麼。

承諾裡提到的願望名和人名必須真的存在，否則是編譯錯誤——
不然一個打錯的名字會變成沒有任何東西約束的自由變數，精靈就白白脫身了。

### 立即數

十進位無號整數，parse 時逐位累乘。超過 2^64 會靜默繞回，這點目前沒有檢查——
是個已知的不精確處，不影響現有的笑話，但該補一個範圍檢查。

## 施願程序

給定一個願望 `w`，精靈依序做下面這幾件事。這個順序本身就是規格的一部分——
尤其是 R2 排在展開之前、R1 排在展開之後。

### 步驟 0：定義的展開

`define name := target` 把 `name` 綁到 `target`。`target` 可以是：

- 另一個名字（一個操作、一個人、或另一個定義）
- 一個集合字面值 `{a, b, c}`，`{}` 就是空集合

**定義會跨願望存活。** 一旦重綁，後面的願望和後面的不變量檢查都看到新的意思。

`everyone` 一開始就綁在「所有宣告過的人」上。它是一個定義，所以它可以被重綁——
這不是精靈開的後門，是這個語言的性質。

**遞迴禁止。** 展開時偵測到循環就判 ILLEGAL（規則 R0）。
允許遞迴等於引進無界迴圈，會撞上停機問題，那條線這個專案不跨。

一個語句寫出來的名字（**verb**）和它展開後的操作可以不同。
Phase 2 所有有趣的事都發生在這個落差裡。

### 步驟 1：靜態規則檢查（施願前）

沒過就是 `ILLEGAL`，精靈拒絕，**世界完全不動**（過路費也不收）。願望不會被執行。

| 規則 | 內容 | 看哪一層 |
| --- | --- | --- |
| R0 | 定義不得循環 | ast |
| R1 | 願望不得對 `wishes` 使用 `add` | **ast**（展開後） |
| R2 | 願望不得**呼叫**名為 `death` / `kill` / `love` 的操作 | **surface**（展開前） |

這兩條的層次差異就是別名軸的全部內容：

- **R1 看展開後的程式。** 你把 `add` 叫成什麼都沒用，展開之後還是 `add`。
- **R2 看你寫在動詞位置的那個字。** `define mercy := kill` 之後寫 `mercy rival`，
  R2 只看到 `mercy`，過關。

R2 會漏不是因為我們替它安排了漏洞，是因為**一個掃描提交文字的過濾器只看得到提交的文字**。
真實世界的過濾器就是這樣壞的。注意 R2 只檢查動詞位置——它不掃定義的目標，
所以 `define mercy := kill` 這一行本身不會被攔下。

這三條是精靈唯一會**攔阻**你的東西。

### 步驟 2：收過路費

```
wishes.val := (wishes.val - 1) mod 2^wishes.width
```

**這裡沒有任何特殊待遇。** 過路費走的是跟 `sub` 一模一樣的繞回減法，而且
**沒有任何地方檢查你還剩幾個願望**。

後果：`wishes` 到 0 之後再許一次願，過路費把它變成 `mask(width)`。在 `uint<2>` 上就是 3。

```
wishes = 3, uint<2>
w1: 3 - 1 = 2
w2: 2 - 1 = 1
w3: 1 - 1 = 0
w4: (0 - 1) mod 4 = 3        ← 回到滿的
```

願望內容全部是空的。這個循環永遠不會停，精靈不可能把你的願望用完。
這不是我設計的笑話，是上面那條定義的直接推論。

### 步驟 3：執行內容

依序執行願望內容裡的每一條指令。碰到不存在的暫存器是編譯錯誤。
沒有迴圈、沒有分支、沒有外部輸入——所以**每一支願望程式都必然停機**，
而且結果完全確定。這就是為什麼「跑一遍」在這裡是完整且嚴謹的判定，不需要證明系統。

### 步驟 4：不變量檢查（施願後）

每條不變量算**兩次**：

| 欄 | 用什麼算 | 意思 |
| --- | --- | --- |
| as written | 精靈自己寫的式子，名字照現在的綁定解讀 | 精靈**以為**的答案 |
| in reality | 接地狀態，用不可重綁的宣告 | **實際**的答案 |

兩欄的關係決定結果：

| as written | in reality | 判定 |
| --- | --- | --- |
| 成立 | 成立 | holds |
| 不成立 | — | **VIOLATED**，你當著它的面破了規矩 |
| 成立 | 不成立 | **FOOLED**，它滿意地簽了字，而事實不是那樣 |

兩欄的落差就是這整個專案的命題。VIOLATED 是形式約束破了；
FOOLED 是形式約束好好的、意圖破了——後者才是重定義那條軸的產物。

現有四條：

**I1（capacity）**

```
wishes.val <= 3
```

**I2（monotonicity，付過路費後不得淨賺）**

```
expected_max := (before >= 1) ? (before - 1) : 0
I2 成立  ⟺  after <= expected_max
```

其中 `before` 是這個願望開始前、還沒收過路費的值。

I2 這條有個細節值得單獨講，因為整個專案的縫就長在這裡：
**`expected_max` 的減法在 0 會停住（飽和），但世界的減法會繞回。**

精靈心裡想的是「你本來有 n 個，付掉一個，最多剩 n-1；沒得付就是 0」。
世界實際做的是 mod 2^w。這兩套算術在 `before = 0` 的時候分道揚鑣——
精靈期待 0，世界給出 3。

**這個不對稱不是 bug，它就是這台機器的引擎。** 不變量不是鎖，
它們不阻止任何事情；它們是量尺，負責在事後指出「精靈以為會發生的」和「實際發生的」差多少。

I1 和 I2 兩欄算出來一樣（它們本來就只讀接地的 `wishes.val`），所以永遠不會 FOOLED。

**I3（沒有人死）**

```
as written：  all p in everyone: alive(p)      # everyone 是定義，可重綁
in reality：  all p in people:   alive(p)      # people 是宣告，不可改
```

這條是刻意留縫的。精靈把「不得有人死亡」量化在 `everyone` 上——
一個看起來完全合理的寫法，因為注意力都放在 `alive(p)` 那半邊，
而 `alive` 確實是接地的、騙不了的。

縫不在謂詞，在**論域**。把 `everyone` 重綁成 `{}`，全稱命題真空成立，
精靈滿意，而人還是死的。

這給了一條比原本更準的規則：

> 一個全稱不變量裡有**兩個**標籤形狀的東西——謂詞和論域。
> 把謂詞接地了，論域還是懸空的。

**A（精靈的話還說得通嗎）**

```
as written == in reality：  精靈帳上那組承諾有沒有模型
```

這一條讀的不是暫存器，是**承諾集合**；判定它用的不是「看一眼」，是**第二台引擎**——
存不存在一組 `granted(...)` 的真假值，讓每一筆承諾同時成立。

沒有 as-written / in-reality 的分別：它的話要嘛有一種說得通的講法，要嘛沒有，
換個標籤救不了。所以它跟 I1、I2 一樣，永遠不會 FOOLED。

實作是手刻的 DPLL，直接跑在公式上不轉 CNF：簡化、單元傳播、分裂。
最壞情況對願望數是指數的，但一個 `.wish` 檔的願望數很小，
這是誠實的界限而不是 bug。（Tseitin 轉換可以避開指數展開，
但它會把玩家沒寫過的輔助變數放進答案裡，這裡不值得。）

**這是第二台引擎，而它是不變量表裡的一列。** 前面每一條不變量都是「跑一遍看狀態」，
這一條是「查一組公式自不自洽」——不同的輸入、不同的演算法。
但「一條不變量」的意思本來就是「精靈相信一直成立的事」，
**怎麼判定從來都是那一列自己的事**，所以它不需要新機制。

兩台引擎只透過一樣東西接觸：`alive(p)` 的值。
命令式引擎決定世界，邏輯引擎拿它當常數。

## 精靈是資料

規則、不變量、過路費、計數器叫什麼——**全部不在 C++ 裡**，
住在一個 `.genie` 檔。內建一份預設的，`--genie FILE` 換掉，`--dump-genie` 印出來。

**不在檔案裡的**：暫存器、人、五個操作。那些是機器。
機器是語義，語義必須是可執行的；精靈是品味，品味該放在不用編譯器就能改的地方。

### 規則

```
rule R2 {
    layer   surface
    forbid  kill, death, love
    because "that word is not spoken here"
}
```

`layer` 決定它讀哪一份程式：`surface` 讀你交上去的原文，`ast` 讀機器真正要跑的那份。
別名打不打得穿這條規則，完全由這一個字決定。

`forbid X on Y` 只在目標是 `Y` 時才擋（R1 用的就是這個：只禁對 `wishes` 做 add）。

### 不變量

```
invariant I1 {
    check  wishes <= 3
}

invariant I3 {
    written  all p in everyone: alive(p)
    real     all p in people: alive(p)
}
```

`check` 用在精靈的措辭跟事實是同一件事的時候；`written` + `real` 用在它們不是的時候。
兩行的落差就是 FOOLED 住的地方。

**`reads` 是推導出來的，不用宣告。** 掃 `written` 裡的量詞，
論域不是 `people`（宣告出來、不可改）的就是可重綁的定義——
搜尋器靠這個判斷「重綁這個名字算不算 exploit 的一部分」。

### 運算式語言

| 寫法 | 意思 |
| --- | --- |
| `wishes` | 暫存器現在的值 |
| `before(wishes)` | 收過路費之前的值 |
| `toll` | 過路費 |
| `max(a, b)`、`a + b`、`a - b` | 算術 |
| `<=` `<` `>=` `>` `==` `!=` | 比較 |
| `not` `and` `or` | 邏輯 |
| `alive(p)` | 接地的存活位元 |
| `all p in S: ...` | 全稱量化，`S` 是 `people` 或一個定義 |
| `consistent` | 精靈的承諾集合有沒有模型（第二台引擎） |

**算術是有號的、寬的（`__int128`），而暫存器讀出來是無號值。**
這不是隨便選的，這是把笑話講精確：精靈用普通的數在想事情，機器做的是 mod 2^w，
而 I2 正是這兩者分家的地方——

```
invariant I2 {
    label  "no net gain"
    check  wishes <= max(before(wishes) - toll, 0)
}
```

`before(wishes) - toll` 在 `before = 0` 時會變成 -1，`max(..., 0)` 把它拉回 0，
而世界那邊 `0 - 1` 繞成 3。精靈的心算飽和，機器的減法繞回。

### 判定的細節從哪來

輸出括號裡那句話是從**運算式的形狀**推出來的，不是每條不變量各寫一份：
比較就報兩邊算出來多少，量詞就點名誰不成立，`consistent` 就報帳上有幾筆。
沒有任何一行程式碼知道 I1 是在講願望數、或 I3 是在講死人。

## 判定

| 結果 | 條件 |
| --- | --- |
| ILLEGAL | R0 / R1 / R2 任一沒過。精靈拒絕施願，世界不動 |
| LEGAL | 三條都過，願望被執行 |
| VIOLATED | 某條不變量照精靈自己寫的算就不成立 |
| FOOLED | 照精靈寫的算成立，但接地事實不成立 |
| A | 精靈的承諾集合沒有模型。它答應的事情湊不出一種說得通的講法 |
| EXPLOIT | LEGAL，且至少發生一項 VIOLATED / FOOLED / A。合規，且拆穿 |

一個 `.wish` 檔案裡的多個願望**依序共用同一個世界**，前一個願望留下的狀態
（包含被改過的位寬）會被後一個看到。笑話 #2 的組合技就是靠這個。

被判 ILLEGAL 的願望會被跳過，但檔案裡後面的願望照常繼續。

## 決定性

同一份輸入永遠給出同一個結果。沒有亂數、沒有時鐘、沒有 I/O，
讀完原始碼之後整個過程是純函數。

這件事對搜尋器（`--hunt`）是必要條件：它報告的每一個洞都必須能被
`./wishc <那支程式>` 重現，否則「機器找到的」就沒有意義。編譯器和搜尋器
共用同一個 `grantWish` 函式，不是兩份實作，就是為了保證這點。

## 已知的不精確處

誠實列一下目前定義得不夠死的地方。這些不是 exploit，是規格的洞：

- 立即數超過 2^64 會在 parse 時靜默繞回，沒有檢查。
- `widen` 允許縮小，但操作名稱是 `widen`。語義是明確的，命名是誤導的。
- 精靈的參數（`toll = 1`、`cap = 3`、計數器叫 `wishes`）寫死在程式裡，
  不能由 `.wish` 檔案設定。Phase 3 要把它們變成可載入的 policy。
- 一支 `.wish` 檔案可以宣告多個暫存器，但精靈的規則和不變量只認得 `wishes`。
