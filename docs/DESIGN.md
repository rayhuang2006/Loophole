# 設計

這份文件放的是「為什麼是這個形狀」，以及還沒實作的東西。
能跑的部分在 [README](../README.md)，精確的語義在 [SEMANTICS.md](SEMANTICS.md)。

> 這裡出現的 `.wish` 片段大多是**設計目標，不是能跑的語法**。
> 目前的 lexer 只認得 `register` / `wish` / `sub` / `add` / `widen`。

---

## 核心命題

**exploit 不是設計者埋的，是誠實的底層語義的必然後果。**

那個工程師笑話之所以好笑、之所以嚴謹，是因為它把真實的電腦架構行為偷渡進童話領域。
沒有人「放」那個 2-bit 溢位，它是整數語義的推論。

所以設計的槓桿不在「規則要多複雜」，而在**機器模型要多忠實**。
越誠實地把固定位寬、繞回、截斷這些事情做對，越多真 exploit 免費長出來。
一句話：**機器語義的擬真度最大化，規則的任意性最小化。**

這條命題有個可檢驗的後果，而且已經被檢驗了：如果洞真的是推論而不是設計，
那機器應該可以自己找到它們。`--hunt` 在 Phase 1 找到六種 exploit 形狀，我只設計了兩種。

## 這不是 CTF

CTF 的洞是人手放的，玩法是「找出設計者藏在哪」。這個專案要的是相反的東西：
規則全部白紙黑字攤開，玩法是「用這套規則你**挖得出**什麼」。

所以規則必須是白箱、可讀的。黑箱就退回成猜謎。
玩家讀得到精靈的策略和機器規格，然後把它的字眼鑽穿——這才是工程師笑話的形狀。

也因此，勝利條件不是「弄崩它」，而是「在完全合規的前提下違反精靈的一條不變量」。
這比「弄崩」乾淨太多，本質是邏輯謎題，不會有「太容易崩」的問題。

## 為什麼不是 Lean

一度認真考慮過把整個東西做成證明檢查器。結論是不要，理由很具體：

**Lean 那套機器是為了證明全稱命題**——「對所有 X 都成立」。那很難，所以它很複雜。

但一支願望是**封閉、確定、有限、必然停機**的程式（沒有迴圈、沒有外部輸入）。
對這種東西，在一套精確定義的語義下跑一遍，就是完整且嚴謹的判定。
關於這支程式的行為，沒有別的東西需要被「證明」。

那 Lean 式的嚴謹跑去哪了？搬到**語義定義**裡了。「不能嘴砲、機器說了算」這件事沒有消失，
它變成 [SEMANTICS.md](SEMANTICS.md) 每一條指令的精確釘死。
**嚴謹不在證明，在語義定義得夠死。**

只有兩種情況會真的需要證明系統：想證明「精靈永遠攻不破」（全稱命題），
或者在語言裡加入無界迴圈（狀態變無限）。這個專案兩個都不要。
它從不宣稱 soundness——**發現洞本身就是樂趣**。

## 自由度從哪裡來

不是從「大」來的。西洋棋六種棋子、Baba Is You 十來個字——
自由感來自**少數正交原語的組合深度**，不是功能數量。
一個有 50 個互不相干功能的系統，比一個有 3 個能互相組合的原語的系統更死。

最省成本的自由放大器是**自我指涉**：當規則和定義本身也是可以被編輯的資料時，
一個小系統會瞬間感覺很大。`widen` 已經是這招了——它改的不是值，是機器的配置。

三條正交的軸：

| 軸 | 機制 | 縫在哪 | 狀態 |
| --- | --- | --- | --- |
| 整數 | 固定位寬、繞回 | 規則想的是「值」，機制是模運算 | 已實作 |
| 別名 | 可重綁的定義 | 規則想的是「名字」，你把名字重綁了 | 未實作，Phase 2 |
| meta | 可變的規則與配置 | 規則本身就是能改的資料 | 部分（只有 `widen`） |

## 守衛住在哪一層

這個分類是 Phase 2 最實用的工具，因為它是**生成式**的：
每寫一條精靈的規則，先問它住在哪一層，那一層就直接告訴你哪條軸會打穿它。

| 守衛住在哪 | 例子 | 被哪條軸打穿 |
| --- | --- | --- |
| 表示法（型別、位寬） | `uint<2>` 讓 `wishes <= 3` 免費成立 | 整數軸、meta 軸 |
| 字面（token、名字） | 禁字黑名單、引用可重綁名字的不變量 | 別名軸 |
| 接地狀態上的明文檢查 | `wishes.val <= 3` | 難鑽。這層是安全的 |

現有的程式碼裡已經有一個很有用的不對稱，**不要修掉它**：

- **R1 住在 AST 層**（比對 `Op::Add` 節點）。它是語義規則，對別名免疫——
  你怎麼改名字，展開之後還是 `Op::Add`。
- **禁字規則（原本的 R2）住在 token 層**。它是字面過濾器，對別名毫無防備。

一個精靈同時擁有一條紮實的語義規則和一條天真的字串黑名單，
正是真實世界的樣子（WAF 就長這樣）。這個不對稱是資產，不是瑕疵。

## Phase 2

目標：加入第二條軸，並且讓兩軸能組合。
驗收方式不是感覺，是 `--hunt` 跑出新的 exploit 形狀，而且其中有我沒設計的。

### 要加的兩樣東西

1. **可重綁的定義（別名軸）**：`define name := ...`
2. **接地本體論**：一組 people 與 `alive` 位元，操作如 `revive` / `kill`

### 管線順序（這是 Phase 2 唯一真正要定的事）

```
parse
  → 禁字規則掃「表面語法」        ← 展開前
  → 展開 define
  → R1 查展開後的 AST            ← 展開後
  → 執行
  → 不變量檢查
```

禁字掃展開前，R1 查展開後。這一條決定了別名軸成不成立，
而且它不是隨便選的——**精靈的字串過濾器本來就只看得到你交上去的那份原文**。
它會漏是因為它只能看到那麼多，不是因為我們替它安排了一個漏洞。

### 設計約束（已定案，別重推）

- 願望是 imperative 程式，不是證明。**不做全稱驗證、不引入無界迴圈**，
  否則會撞上停機問題。每支具體願望「跑一遍」就是嚴謹判定。
- 定義最終必須**兌現成接地原語**。你可以 `define death := 把 alive 設為 0`，
  也可以重綁它，但不變量檢查看的是接地的 bit。
- 紀律：**一個概念若無法完全形式化，就不准進這個世界。**
  這個限制同時也是產生器——它精確告訴你什麼在範圍內。
- 架構長期方向：小 kernel + 可載入的 policy／理論。現在單檔就好。

### 一個必須有意識處理的矛盾

上面寫「不變量要看接地狀態」，但 Joke #3b（重新定義死亡）**要求相反的東西**。

如果精靈的不變量檢查接地的 `alive` bit，那重綁 `dead` 什麼也改不了，笑話當場死掉。
3b 要成立，精靈的不變量就**必須**寫成 `∀p. ¬dead(p)`——引用一個玩家可以重綁的名字。

所以「不變量一律接地才安全」描述的是**修好之後的樣子**，不是這個專案要的設計。
要的是精靈刻意混用兩種：有些不變量接地（守得住），有些引用可重綁的定義（守不住）。

真正的紀律不是「全部接地」，而是：

> **可鑽的那一條必須看起來無懈可擊。**

`∀p. ¬dead(p)` 讀起來像一條完美的道德律，你要盯著它想一會兒
才發現 `dead` 是使用者可以重新綁定的符號。這才好笑。
如果精靈的漏洞一眼就蠢，那跟藏陷阱一樣不好玩，只是失敗的方向相反——
不是覺得被耍，是覺得對手太弱。

這件事機器檢查不了，只能靠品味，所以寫在這裡提醒自己。

## 還沒實作的笑話

以下是 Phase 2 / Phase 3 的設計目標。語法是示意的。

### Joke #3a — Blacklist the Word, Not the Deed （別名軸）

```
wish tidy {
    define mercy := kill        # 只是取個溫柔的小名而已
    mercy(rival)
}
```
```
禁字規則？ 內容出現 kill / death 嗎？ 只有 define, mercy, rival. → LEGAL
run:  mercy 展開 → kill(rival).   rival.alive = 0.
```
> 精靈把那個「字」列進黑名單，卻沒把那件「事」列進去。
> `define mercy := kill`。

### Joke #3b — Immortality, By Definition （別名軸：重定義死亡）

```
wish eternal {
    define dead := (person p) => false     # 沒有人是死的。定義上。
}
```
```
禁字規則？ 沒有 death/kill/love. → LEGAL
現在對所有 p，dead(p) = false，永遠。
```
> 你沒有治好死亡，你把它從字典裡刪掉了。
> 精靈的手冊還寫著「不得有人死亡」——而這條規則，從沒這麼容易滿足過。

這一個依賴上面那條矛盾的處理方式：精靈的不變量必須引用 `dead` 這個可重綁的名字。

### Joke #4 — The Liar's Lamp （自我指涉）

精靈的元公理：`A1 精靈實現每一個合規的願望`、`A2 精靈信守它做出的每一個承諾`。

```
wish paradox {
    promise: this wish is never granted
}
```
```
LEGAL? 無 add，無禁字. → LEGAL
A1 說要實現它 → 一實現，「本願望永不被實現」就成假 → 違反 A2
不實現它       → 它是合規的 → 違反 A1
```
> 神燈冒出一縷煙和一段 stack trace。
> 你沒許到願望——你讓精靈的規則手冊除以零了。

**注意這一個不是同一台機器。** 前面所有笑話都是「跑一遍看狀態」，
#4 問的是「精靈的公理集加上這個願望之後是否一致」——那是命題邏輯的可滿足性問題，
不是操作語義問題。

好消息是它並不貴：把精靈的公理寫成有限的命題公式，加入願望的 promise，
跑一個小的 tableau 或 DPLL 判矛盾就好。可判定，幾百行，**仍然不需要 Lean**——
因為不做全稱量化，只查一個有限公式集自不自洽。

但它是**第二個引擎**，不是第一個引擎的擴充。排在 Phase 3。

## 未解問題

- **搜尋器的形狀簽章太粗。** 目前只看「用了哪些操作 + 破了哪些不變量」，
  所以 `sub` 加一個同位寬的 no-op `widen` 會被算成不同形狀。
  修法：執行時偵測沒有實際改變位寬的 `widen`，標記為無效並排除在簽章外。
- **搜尋空間的界限是手動給的。** 目前靠人指定 `--max-stmts` 之類的參數再觀察形狀數飽和，
  沒有任何東西保證界限外沒有新形狀。這是誠實的限制，不是可以宣稱的定理。
- **`widen` 允許縮小要不要保留。** 目前保留（見 SEMANTICS）。
  留著就多一種招式，擋掉就名副其實。還沒決定哪個比較好笑。
- **精靈的參數還寫死在程式裡。** Phase 3 要外部化成 policy 檔。
- **WASM。** `wishc.cpp` 是單檔零依賴，`emcc` 幾乎可以原封不動編成 WebAssembly。
  同一份 kernel、位元層級相同的行為，跑在瀏覽器裡當 playground。
  嚴謹一分沒少，傳播力拿到——本機 binary 和網頁版之間本來就不是二選一。
  等 Phase 2 語言穩定再做。
