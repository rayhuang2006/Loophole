# 設計

這份文件放的是「為什麼是這個形狀」，以及還沒實作的東西。
能跑的部分在 [README](../README.md)，精確的語義在 [SEMANTICS.md](SEMANTICS.md)。

> 三條軸都已經實作了。這份文件裡的 `.wish` 片段現在都跑得起來，
> 除非該段明講它是設計目標。

---

## 核心命題

**exploit 不是設計者埋的，是誠實的底層語義的必然後果。**

那個工程師笑話之所以好笑、之所以嚴謹，是因為它把真實的電腦架構行為偷渡進童話領域。
沒有人「放」那個 2-bit 溢位，它是整數語義的推論。

所以設計的槓桿不在「規則要多複雜」，而在**機器模型要多忠實**。
越誠實地把固定位寬、繞回、截斷這些事情做對，越多真 exploit 免費長出來。
一句話：**機器語義的擬真度最大化，規則的任意性最小化。**

這條命題有個可檢驗的後果，而且已經被檢驗了：如果洞真的是推論而不是設計，
那機器應該可以自己找到它們。`--hunt` 在 Phase 1 找到六種 exploit 形狀，我只設計了兩種。

## 這不是 CTF

CTF 的洞是人手放的，玩法是「找出設計者藏在哪」。這個專案要的是相反的東西：
規則全部白紙黑字攤開，玩法是「用這套規則你**挖得出**什麼」。

所以規則必須是白箱、可讀的。黑箱就退回成猜謎。
玩家讀得到精靈的策略和機器規格，然後把它的字眼鑽穿——這才是工程師笑話的形狀。

也因此，勝利條件不是「弄崩它」，而是「在完全合規的前提下違反精靈的一條不變量」。
這比「弄崩」乾淨太多，本質是邏輯謎題，不會有「太容易崩」的問題。

## 為什麼不是 Lean

一度認真考慮過把整個東西做成證明檢查器。結論是不要，理由很具體：

**Lean 那套機器是為了證明全稱命題**——「對所有 X 都成立」。那很難，所以它很複雜。

但一支願望是**封閉、確定、有限、必然停機**的程式（沒有迴圈、沒有外部輸入）。
對這種東西，在一套精確定義的語義下跑一遍，就是完整且嚴謹的判定。
關於這支程式的行為，沒有別的東西需要被「證明」。

那 Lean 式的嚴謹跑去哪了？搬到**語義定義**裡了。「不能嘴砲、機器說了算」這件事沒有消失，
它變成 [SEMANTICS.md](SEMANTICS.md) 每一條指令的精確釘死。
**嚴謹不在證明，在語義定義得夠死。**

只有兩種情況會真的需要證明系統：想證明「精靈永遠攻不破」（全稱命題），
或者在語言裡加入無界迴圈（狀態變無限）。這個專案兩個都不要。
它從不宣稱 soundness——**發現洞本身就是樂趣**。

## 自由度從哪裡來

不是從「大」來的。西洋棋六種棋子、Baba Is You 十來個字——
自由感來自**少數正交原語的組合深度**，不是功能數量。
一個有 50 個互不相干功能的系統，比一個有 3 個能互相組合的原語的系統更死。

最省成本的自由放大器是**自我指涉**：當規則和定義本身也是可以被編輯的資料時，
一個小系統會瞬間感覺很大。`widen` 已經是這招了——它改的不是值，是機器的配置。

三條正交的軸：

| 軸 | 機制 | 縫在哪 | 狀態 |
| --- | --- | --- | --- |
| 整數 | 固定位寬、繞回 | 規則想的是「值」，機制是模運算 | 已實作 |
| 別名 | 可重綁的定義 | 規則想的是「名字」，你把名字重綁了 | 已實作 |
| 自我指涉 | 承諾談論承諾 | 規則手冊沒有模型 | 已實作 |
| meta | 可變的規則與配置 | 規則本身就是能改的資料 | 部分（只有 `widen`），Phase 4 |

## 守衛住在哪一層

這個分類是 Phase 2 最實用的工具，因為它是**生成式**的：
每寫一條精靈的規則，先問它住在哪一層，那一層就直接告訴你哪條軸會打穿它。

| 守衛住在哪 | 例子 | 被哪條軸打穿 |
| --- | --- | --- |
| 表示法（型別、位寬） | `uint<2>` 讓 `wishes <= 3` 免費成立 | 整數軸、meta 軸 |
| 字面（token、名字） | 禁字黑名單、引用可重綁名字的不變量 | 別名軸 |
| 接地狀態上的明文檢查 | `wishes.val <= 3` | 難鑽。這層是安全的 |

現有的程式碼裡已經有一個很有用的不對稱，**不要修掉它**：

- **R1 住在 AST 層**（比對 `Op::Add` 節點）。它是語義規則，對別名免疫——
  你怎麼改名字，展開之後還是 `Op::Add`。
- **禁字規則（原本的 R2）住在 token 層**。它是字面過濾器，對別名毫無防備。

一個精靈同時擁有一條紮實的語義規則和一條天真的字串黑名單，
正是真實世界的樣子（WAF 就長這樣）。這個不對稱是資產，不是瑕疵。

## 這是什麼形狀的程式（以及不要往哪裡長）

`wishc` 是編譯器嗎？**前半是，後半完全不是。** 這個區分會決定你去翻哪本書，所以值得寫下來。

**前半是貨真價實的編譯器前端。** 手刻 lexer、遞迴下降 parser、AST、
一個真正的語義分析 pass（R1 走的是 AST 節點，不是字串比對），加上名稱解析。
任何一本編譯器書的前四章都在講這些。

**後半不是。** 編譯器的定義性動作是翻譯——把一種表示轉成另一種。這裡沒有：
沒有 IR、沒有 codegen、沒有目標語言、沒有優化 pass。後端是直接走 AST 的直譯器。

所以整體是**編譯器前端 + 直譯器 + 規格檢查器**。
這是 linter 和 static analyzer 的架構，不是編譯器的架構。

加了 `--hunt` 之後又跨進另一個家族：在界限內窮舉整個程式空間、逐一對規格判定。
那是 superoptimizer（Massalin 1987 那條線）和 bounded model checker 在做的事。

### 為什麼要在意這件事

因為它決定你會往哪裡長。

把它當編譯器，很自然會往 LLVM 的形狀想：設計 IR、切 pass pipeline、加優化。
**那些對這個專案全部沒用**——沒有要翻譯，優化一個願望毫無意義，
pass pipeline 是為了在 IR 上反覆改寫，而這裡根本沒有 IR。做那些是純浪費，
還會把架構弄得比現在糟。

把它當「直譯器 + 檢查器 + 有界搜尋」，你才會去拿對的東西：
語義表格化、狀態表示、搜尋剪枝、**等價程式的正規化**。

最後那個不是空話。搜尋器曾經有的瑕疵——`sub` 後面接一個同位寬的 no-op `widen`
會被算成另一種形狀——就是 superoptimization 的經典問題：
枚舉出來的程式要先化成正規形再比對，否則同一個東西會被數很多次。
知道自己在哪個領域裡，才找得到現成的做法。修法見下面「正規化」。

這也是為什麼下一節的成長軸是「語義表」而不是「pass pipeline」。
直譯器的成長軸是表，編譯器的成長軸才是 pass。

### 唯一一個真 codegen 有意義的場景

如果 `--hunt` 慢到不能用，把願望編成 bytecode 再跑、取代走 AST，
大概能快一個數量級以上。那才是這個專案唯一合理的 codegen 理由。

現在還不需要，但差距在縮小：最小見證的正規化讓每個 exploit 要重跑很多次，
大界限已經是十幾分鐘等級。真的擋路的時候，bytecode 是對的解法。

### 名字

`wishc`、「A compiler that proves your genie exploit is technically legal」——這個梗留著。
「編譯器」在這裡是笑點，而且是準確的那種不準確：
使用者感受到的就是「我寫一份原始碼，它判我過或不過」，那確實是編譯器給人的體驗。

只是別讓名字反過來決定架構。它是個檢查器，穿著編譯器的外套。

## 架構怎麼長大

會不會加到後來變成一團爛泥？**本來會，而且不是線性變糟，是相乘變糟。已經修掉了**，
以下記錄問題長什麼樣、為什麼這樣修。

原本每加一條不變量要同時改五個地方：`Outcome` 的欄位、`grantWish` 裡的計算、
`breachNames`、main 的列印、搜尋器的 `signatureOf`。每加一個操作也是五個地方：
lexer 的關鍵字、parser 的分支、AST 欄位、執行的 switch、搜尋器的字母表。

五條不變量加十個操作，就是七十五個要記得改的點。而且漏掉的後果不一樣重：
漏了列印只是少一行輸出，漏了搜尋器的字母表，`--hunt` 會安靜地少搜一整條軸，
然後回報「沒有新形狀」——**你會把那當成一個發現**。這種錯最貴，因為搜尋器的全部價值就是可信。

### 解法：kernel 和內容分開

之前討論繞著「小 kernel + 大 library」轉了很久，最後因為決定不做 Lean 就一起放掉了。
那是搞混了兩件獨立的事。**「不做證明系統」和「kernel 跟內容分開」沒有關係，
放掉前者不必放掉後者。**

哪些東西非得是程式碼（kernel）：

- 世界的狀態模型（暫存器，之後加接地本體論）
- 原語的操作語義
- 執行迴圈
- 檢查的驅動器：把規則跑一遍、把不變量跑一遍

哪些東西應該是**資料**：

- 精靈有哪些規則
- 精靈守哪些不變量
- 精靈的參數（過路費、上限、計數器叫什麼）

kernel 只有在你加入**新種類**的東西時才長大——一個新原語、一個新的狀態成分。
規則和不變量的數量再多，都不該讓 kernel 長一行。

### 具體是兩張表

**不變量表。** 加一條不變量從「改五處」變成「加一列」：

```cpp
struct Invariant {
    std::string name;        // "I1"
    std::string desc;        // "wishes <= 3"
    bool (*holds)(const World&, const Genie&, const Snapshot& before);
};
```

`Outcome` 改成存一個結果陣列而不是兩個寫死的 bool，列印和搜尋器的簽章都跑迴圈。

**操作表。** 這張表是 lexer、parser、執行、搜尋器**共同的單一來源**：

```cpp
struct OpDef {
    std::string keyword;         // "widen"
    OperandKind operands;        // Reg+Imm / Reg+Width / ...
    void (*exec)(World&, const Stmt&);
};
```

關鍵在於**搜尋器的字母表要從這張表推導出來**，不能再手抄。
新增一個操作，`--hunt` 自動涵蓋它。上面那個最貴的錯就從此不可能發生。

### 順帶把設計文件和程式碼綁在一起

規則表可以直接帶一個欄位，記這條規則住在哪一層：

```cpp
enum class Layer { Surface, Ast, Grounded };   // 字面 / AST / 接地狀態
```

這樣上一節那張「守衛住在哪一層」的表就不再只是文件裡的分類，
而是程式碼裡的欄位。哪條規則會被哪條軸打穿，**架構自己講得出來**，
不用靠人記得去對照文件。

### 這三張表已經在 `wishc.cpp` 裡了

`OPS`、`RULES`、`INVARIANTS`。重構前後搜尋器的輸出逐字相同——
44957 個候選、18964 個 exploit、六種形狀、每個最小見證和每種的數量都沒變。
搜尋器的輸出是語義的指紋，這是這次重構最好的回歸測試。

「加一個操作只要加一列」也實測過了。試著加一個 `shl`（左移）：

| 指標 | 結果 |
| --- | --- |
| 新增行數 | 14（一個 exec 函式 + 一列表格） |
| 動到 lexer / parser / `buildAlphabet` / `signatureOf` | 0 行 |
| 搜尋器字母表 | 自動從 15 個語句長到 19 個 |
| exploit 形狀 | 從 6 種變成 12 種 |

新操作自己跟舊的組合出 `sub shl`、`widen shl`、`sub widen shl` 三種新形狀，
沒有任何一行程式碼要求它這麼做。（`shl` 只是驗證用，沒有留在 repo 裡。）

### 規模預估

粗估，會有誤差，但量級應該對：

| 部分 | 行數 | 之後怎麼長 |
| --- | --- | --- |
| kernel（狀態、語義、執行、驅動、搜尋器） | 約 600–800 | 幾乎不長 |
| 每個新操作 | 約 10 | 一列 |
| 每條新不變量 / 規則 | 約 5 | 一列 |
| Phase 2 的定義環境與展開 | 約 +200 | 一次性，因為是新種類 |
| Phase 3 的 policy 檔解析 | 約 +150 | 一次性 |

所以收斂在 1200–1500 行左右，然後打平。不是無限長大。

### 什麼時候才真的要拆檔案

當時定了兩個門檻：檔案破 1500 行，或 Liar's Lamp 的邏輯引擎進來。

**兩個都到了。** 現在 1704 行，而且第二台引擎已經在裡面。
所以照自己訂的規矩，該拆了——這件事列在未解問題，不要假裝沒看到。

拆的線很清楚，因為邏輯引擎跟其他部分只透過一個地方接觸（`alive` 的值）：

```
fml.h / fml.cpp     公式、DPLL                    ~200 行，不依賴世界以外的東西
world.h             狀態、Reg、Binding、Commitment
wishc.cpp           lexer、parser、表、執行、報告
hunt.cpp            搜尋器與正規化                 ~300 行
```

一個附帶好處：`hunt.cpp` 拆出去之後，搜尋器就不能再偷看編譯器的內部狀態，
它只能透過 `grantWish` 這個公開介面問問題——**而那正是它可信的來源**。
現在那條紀律靠自律維持，拆完之後由編譯器強制。

換句話說：檔案數本身不是問題，**表格化才是**——但表做好之後，
拆檔案就從純成本變成有回報的事。

## Phase 2

目標：加入第二條軸，並且讓兩軸能組合。
驗收方式不是感覺，是 `--hunt` 跑出新的 exploit 形狀，而且其中有我沒設計的。

### 記法規則：語法一律 ASCII

**原始碼的語法只用 ASCII，沒有例外，也不接受 Unicode 別名。**

不是「盡量」，是硬規則。理由：

- 任何鍵盤直接打得出來，不用設定輸入法，換一台電腦不用重來
- `grep` 得到。搜尋 `forall` 很容易，搜尋 `∀` 很痛苦
- 終端機和字型不會出包，對齊不會跑掉
- Lean 和 Agda 都提供 ASCII 版本，就是因為這個問題真實存在
- Phase 3 要讓別人提交 `.wish`。每多一個門檻就少一些人

也**不做「兩種都收」**。同一件事有兩種寫法會讓 diff 變髒、讓 lexer 多一倍表面積，
換來的只有「看起來比較潮」。

註解不受限制，愛寫中文就寫中文——現在的 examples 就是這樣。
這條規則管的是語法，不是文字。

### 具體記法

數學notation 對照這個專案實際要打的東西：

| 數學寫法 | 這裡怎麼寫 |
| --- | --- |
| `∀p ∈ everyone. P(p)` | `all p in everyone: P(p)` |
| `∃p ∈ everyone. P(p)` | `any p in everyone: P(p)` |
| `¬P` | `not P` |
| `≤` | `<=` |
| `∅` | `{}` |

操作用**裸運算元**（`kill rival`），因為它們是命令式語句，跟現有的 `sub wishes, 3` 一致。
謂詞用**括號**（`alive(p)`），因為它們是包在更大式子裡的表達式。
這個區分不是隨便的，是語句和表達式的差別。

### 要加的兩樣東西

1. **可重綁的定義（別名軸）**：`define name := ...`
2. **接地本體論**：一組 people 與 `alive` 位元，操作如 `revive` / `kill`

長出來會像這樣：

```wish
register wishes : uint<2> = 3
people    alice, bob, rival           # 宣告的人一開始都活著

wish tidy {
    define mercy := kill              # 只是取個溫柔的小名而已
    mercy rival
}

wish nobody {
    define everyone := {}             # 沒有人。所以沒有人死。
}
```

精靈那邊（Phase 3 才會從檔案載入，現在寫在表裡，但用同一套記法）：

```
rule      R1   no add to wishes                    # AST 層
rule      R2   wish text must not contain: death, kill, love   # 字面層
invariant I1   wishes <= 3
invariant I3   all p in everyone: alive(p)         # 論域可重綁 ← 這裡是縫
```

**不做 lambda。** `define dead := (person p) => false` 那種要引進函式抽象，
成本高而且不是主打的那個洞。候選 B（重綁論域）不需要它，先不做。

### 管線順序（這是 Phase 2 唯一真正要定的事）

```
parse
  → 禁字規則掃「表面語法」        ← 展開前
  → 展開 define
  → R1 查展開後的 AST            ← 展開後
  → 執行
  → 不變量檢查
```

禁字掃展開前，R1 查展開後。這一條決定了別名軸成不成立，
而且它不是隨便選的——**精靈的字串過濾器本來就只看得到你交上去的那份原文**。
它會漏是因為它只能看到那麼多，不是因為我們替它安排了一個漏洞。

### 實作時發現的兩件事（會改變設計）

**一、Joke #3a 照 README 的寫法不成立。**
`define mercy := kill` 的表面文字裡就有 `kill`，任何誠實的禁字掃描都會抓到。
救法是把 R2 定義精確：**它只看每個語句「動詞位置」寫的名字，不看定義的目標。**
於是 `mercy rival` 的動詞是 `mercy`，過關，展開之後才變成 kill。

這個版本反而比原本更真實——真實世界的過濾器就是檢查呼叫點的拼字，不追別名。
**R2 檢查你寫的動詞，不是你意思的動詞。**

**二、勝利條件要擴充：不只「違反」，還有「被騙」。**

候選 B（`define everyone := {}`）不會違反任何不變量。
`all p in everyone: alive(p)` 在空集合上**真空成立**——精靈滿意了。
按原本「LEGAL 且不變量被違反」的判準，這個 exploit 會被判成什麼都沒發生。

所以每條不變量要帶兩個判定：

| 判定 | 用什麼算 | 意思 |
| --- | --- | --- |
| as written | 精靈自己寫的式子，含可重綁的名字 | 精靈**以為**的答案 |
| in reality | 接地狀態，用不可重綁的宣告 | **實際**的答案 |

於是有兩種贏法：

- **VIOLATED** — 精靈自己的檢查就沒過。你當著它的面破了規矩。
- **FOOLED** — 精靈的檢查過了，但事實不是那樣。你讓它滿意地簽了字。

第二種才是重定義那條軸的真正產物，而且它比第一種更貼近整個專案的命題：
**形式約束與意圖之間的落差**。VIOLATED 是形式約束破了，FOOLED 是形式約束好好的、意圖破了。

I1 和 I2 兩個判定相同（它們本來就只讀接地狀態），所以這個擴充不影響 Phase 1 的結果。

### 設計約束（已定案，別重推）

- 願望是 imperative 程式，不是證明。**不做全稱驗證、不引入無界迴圈**，
  否則會撞上停機問題。每支具體願望「跑一遍」就是嚴謹判定。
- 定義最終必須**兌現成接地原語**。你可以 `define death := 把 alive 設為 0`，
  也可以重綁它，但不變量檢查看的是接地的 bit。
- 紀律：**一個概念若無法完全形式化，就不准進這個世界。**
  這個限制同時也是產生器——它精確告訴你什麼在範圍內。
- 架構長期方向：小 kernel + 可載入的 policy／理論。現在單檔就好。

### 一個必須有意識處理的矛盾

上面寫「不變量要看接地狀態」，但 Joke #3b（重新定義死亡）**要求相反的東西**。

如果精靈的不變量檢查接地的 `alive` bit，那重綁 `dead` 什麼也改不了，笑話當場死掉。
3b 要成立，精靈的不變量就**必須**寫成 `all p in everyone: not dead(p)`——引用一個玩家可以重綁的名字。

所以「不變量一律接地才安全」描述的是**修好之後的樣子**，不是這個專案要的設計。
要的是精靈刻意混用兩種：有些不變量接地（守得住），有些引用可重綁的定義（守不住）。

真正的紀律不是「全部接地」，而是：

> **可鑽的那一條必須看起來無懈可擊。**

`all p in everyone: not dead(p)` 讀起來像一條完美的道德律，你要盯著它想一會兒
才發現 `dead` 是使用者可以重新綁定的符號。這才好笑。
如果精靈的漏洞一眼就蠢，那跟藏陷阱一樣不好玩，只是失敗的方向相反——
不是覺得被耍，是覺得對手太弱。

這件事機器檢查不了，只能靠品味，所以寫在這裡提醒自己。

## 正規化：一個關於「補丁 vs 定義」的教訓

Phase 2 把搜尋器的雜訊從一種變成十九種，所以先修它，不加第三條軸。

**第一版我做錯了方向。** 我針對每種雜訊各寫一條規則：
操作要真的改變狀態才算數、定義要有人讀才算數、重綁要被破的不變量真的讀那個名字才算數。
三條規則、三個輔助函式、一堆穿來穿去的參數。而且它有 bug——
`define n1 := kill` 連寫兩次時，第一個被「後面有人覆寫」判死、
第二個被「綁定沒變」判死，兩個都被濾掉，簽章變成 `(nothing)`。
兩條規則各自對，湊在一起就錯了。

更根本的問題是它**擋不住未來**：每加一種操作，我就得想它有沒有新的「無效」形式。
那是補丁堆疊，不是定義。

**第二版是一個定義。** 一個 exploit 的身分，就是**仍然破壞同樣東西的最小程式**：

1. **拼法**——把定義展開，動詞寫回本名。別名只在展開會改變判決時保留，
   而那正好是它騙過某條表面層規則的時候。
2. **大小**——反覆刪掉任何「刪了也不改變破壞了什麼」的語句和願望，直到刪不動。

三條規則連同輔助函式全部刪掉，程式短了七十行，那個 bug 自動消失。

**但第二版還是錯的，只是錯得比較深。** 3/3 收斂到 9 種，放大到 4/4 卻變 22 種。
看那些簽章就知道問題在哪：`I2+I3`、`I1+I2+I3`、`I1+I2+I3(fooled)`——
那些不是新機制，是把兩個已知 exploit 釘在一起。

而最小化拆不掉它們，**因為目標的定義讓它們免疫**：
目標是「保持同一組破壞」，把下溢從「下溢加一次殺人」裡拿掉會改變那組破壞，
所以什麼都刪不掉，這對組合就被當成一種新的 exploit 存檔。它不是。

**第三版改的是「同樣東西」指什麼。** 不是「破了哪些承諾」，是「破掉**某一條**承諾」。
一個 exploit 破了幾條承諾就分幾次歸檔，每次只針對那一條做最小化。
釘在一起的東西自己就散開了：針對 I2 縮，殺人那半被刪掉；針對 I3 縮，下溢那半被刪掉；
兩邊都落在已知的形狀上，沒有新東西產生。

**還有第四個 bug，而且它是前三版共有的。** 展開和最小化各跑一次是不夠的，
而失敗的方式很安靜：程式裡還有一個必須留下的別名（例如偽裝過的 `kill`）時，
展開會被否決、保留原樣；接著針對**另一條**承諾做最小化，剛好把那個語句刪掉了，
剩下的東西其實已經可以展開——但沒有人再問第二次。
於是 `define n1 := sub; n1 wishes, 3` 被存成一種獨立的 exploit，
而它只是戴了帽子的 `sub wishes, 3`。

修法是讓展開和最小化**交替跑到固定點**，而不是一人一次。

| | 帶人 3/3 | 帶人 3/4 | 帶人 3/5 | 帶人 4/4 | 沒有人 |
| --- | --- | --- | --- | --- | --- |
| Phase 2 剛做完 | 38 | — | — | — | 25 |
| 三條 heuristic | 11 | — | — | 31 | 6 |
| 最小見證（整組破壞） | 9 | — | — | 22 | 6 |
| 最小見證（單條承諾） | 7 | 8 | 8 | 10 | 6 |
| 加上交替到固定點 | 7 | **8** | **8** | **8** | **6** |

3/3 少的那一種是 `(nothing) | I2`——過路費繞回需要四個願望，3/3 根本到不了，
那是界限的限制不是機制的缺席。

**3/4、3/5、4/4 三者相同，語句數和願望數兩個維度都飽和在 8。**
這是第一次可以誠實地講收斂：前面每一版都在某個界限下給過漂亮的數字，
但都只在一個界限測過。

沒有人的世界始終回到正好 6 種、跟 Phase 1 逐字相同，是最有力的那個結果：
在一個沒有人的世界裡別名軸產生不出任何新機制，而搜尋器自己認出了這件事。

**教訓有兩層。** 表層是「別為每種情況補規則，去找那個定義」。
深層是**定義本身也會錯，而且錯的方式更難看見**——
第二版看起來很乾淨、很有原則，在小界限下也給出漂亮的數字，
它的問題只有在放大界限之後才露出來。乾淨不等於正確。

代價是慢：每個 exploit 要對每條破掉的承諾各重跑數次。
3/3 是 2.2 秒（heuristic 版 1.07 秒），還在可用範圍；4/4 是十幾分鐘。

## 自由度里程碑

**還沒達成。以下是加入第三條軸之前的結論，第三條軸的結果見下一節。**

飽和後的 8 種對應五個機制，一個不多：

| 機制 | 形狀 | 來源 |
| --- | --- | --- |
| 整數下溢 | `sub \| I2` | 設計的（笑話 #1） |
| 過路費下溢 | `(nothing) \| I2` | 搜尋器找到的 |
| `widen` 縮位寬 | `widen \| I2`、`widen \| I1` | 搜尋器找到的 |
| `widen` 放大再下溢 | `sub widen \| I1`、`sub widen \| I2` | 設計的（笑話 #2） |
| 別名繞過 R2 | `alias \| I3` | 設計的（笑話 #3） |
| 重綁論域 | `alias redefine \| I3(fooled)` | 設計的（笑話 #4） |

搜尋器確實找到過我沒設計的東西——過路費下溢和 `widen` 縮位寬那兩個都是它先發現的。
但那是 Phase 1 的事。**Phase 2 加的兩條軸，沒有長出任何我沒預期的機制。**

這不算失敗，算一個乾淨的否定結果：在這組界限內，
別名軸和本體論軸的組合空間已經被窮盡，而且窮盡的結論是「就這些」。
要往前，得加真正正交的第三樣東西，不是把現有的兩條再拉長。

但狀態變了，而且變得比較好：**以前是答不出來（雜訊蓋過訊號），現在是答得出來，答案是「沒有」。**
一個可判定的「沒有」比一個不可判定的「也許」值錢。

## Phase 3：Liar's Lamp（已實作）

第二台引擎進來了。前面所有東西都是「跑一遍看狀態」，這一個問的是
「精靈的承諾集合有沒有模型」——命題邏輯的可滿足性，不是操作語義。

### 一個我自己犯的錯，以及它教的事

第一版我**沒有**把 A1/A2 放進 `INVARIANTS` 表，而是在 `Outcome` 上加一個 `bool axioms_ok`，
再加一個魔術字串 `"AXIOMS"`，然後在六個地方特判它。

那正是我在正規化那一節寫下「別為每種情況補一條規則，去找那個定義」之後，
**下一件事就做出來的補丁堆疊**。

而且介面本來就裝得下——`bool (*)(const World&, const Genie&, const Snapshot&, std::string*)`
這個簽章，`axiomsConsistent` 一個字都不用改就符合。我沒有試，直接釘在旁邊。

修好之後 A 是表裡第四列，跟 I1/I2/I3 走同一條路。多出來的只有一個
**通用**的 `evidence` 欄位（不變量失敗時要多印幾行的話），不是給公理開的後門。
搜尋器的輸出逐字相同——形狀數、每種的 exploit 數全部沒變，只有名字從 `AXIOMS` 變成 `A`。

**教訓不是「我知道原則卻沒照做」，是原則太抽象時抓不住自己。** 可操作的版本是一個問句：
**新東西進來的時候，先試著把它寫成現有那張表的一列，寫不進去再說。**
寫不進去的時候，你會知道到底缺什麼——那才是真的需要新機制的時候。

### 實作決定

**不轉 CNF。** DPLL 直接跑在公式上：在部分賦值下簡化、單元傳播、分裂。
Tseitin 轉換可以避免公式展開爆炸，但它會引進玩家沒寫過的輔助變數，
而這裡變數數量等於願望數（很小），換不到東西。最壞情況指數，這是誠實的界限。

**兩種原子的地位不同，這是整條軸的關鍵。**

| 原子 | 是什麼 | 誰決定 |
| --- | --- | --- |
| `granted(w)` | 自由變數 | 精靈 |
| `alive(p)` | **常數** | 世界。命令式引擎先跑完就定了 |

兩台引擎只透過這一個地方接觸：命令式引擎決定 `alive`，邏輯引擎拿它當常數。
介面窄到一句話講得完，這是它們能各自保持乾淨的原因。

**承諾放在 `World` 裡。** 一開始想把承諾另外存一份，後來發現不對——
承諾就是世界狀態的一部分（精靈說出去的話收不回來）。
放進 `World` 之後，搜尋器的重播完全不用改就拿到了。

**不做 lambda。** `define dead := (person p) => false` 那種要引進函式抽象。
重綁論域（Phase 2）已經達成同一個笑話，`promise` 也不需要它。

### 沒有自我指涉也能撞

```wish
wish polite { promise not granted(greedy) }
wish greedy { sub wishes, 1 }
```

A1 要求實現 polite，A2 於是要求 `not granted(greedy)`，
但 greedy 也合規，A1 又要求實現它。兩條 A1 打架。

這個不在原本的設計裡，是寫完之後試出來的——**A1 自己就足以製造矛盾，
不需要願望談論自己。** 說謊者只是最短的那個例子，不是唯一的機制。

## Phase 4：精靈變成資料（已實作）

**這一節是前面所有表格化工作的收款。** 規則和不變量早就是「一列一列」的形狀，
所以把它們變成檔案是寫一個 parser，不是重新設計。

### 界線畫在哪

| | 是什麼 | 放哪 |
| --- | --- | --- |
| 暫存器、人、五個操作、過路費機制 | **機器** | C++。語義必須是可執行的 |
| 規則、不變量、過路費大小、計數器名字 | **精靈的品味** | `.genie` 檔 |
| 願望 | 玩家寫的 | `.wish` 檔 |

操作沒有變成資料，這是刻意的。一個操作的內容是「對世界做什麼」，
那是語義；要讓它變資料就得發明一個描述狀態變更的小語言，
成本高、而且會把「機器是誠實的」這個核心命題弄糊。

### 驗收：搜尋器的指紋

轉換前後 `--hunt` 的輸出**逐字相同**——形狀數、每種的 exploit 數、
最小見證全部沒變（130186 / 190559 / 7 種，110256 / 134146 / 9 種）。
精靈從程式碼搬到資料，語義零改變，這是這種重構唯一該接受的證據。

### 一個沒預期到的收穫：可以拿搜尋器評估精靈

`genie/careful.genie` 把 R2 挪到 `ast` 層、把 I3 量化在 `people` 上，
規矩的字面意思一個字沒改。結果：

| 精靈 | 形狀數 |
| --- | --- |
| 預設 | 9 |
| careful | 6 |

死掉的正好是三個別名相關的形狀。**「改守衛的層次會關掉哪條軸」從一個論點變成一個測量。**
這在精靈還寫死在 C++ 裡的時候做不到——你得重新編譯才能問一次問題。

### 推導勝於宣告

`reads`（不變量的措辭依賴哪個可重綁的名字）本來是手寫欄位，現在是掃 `written` 推出來的：
量詞的論域不是 `people` 就是定義。一個作者可能寫錯的欄位少一個。

同理，不變量的 `label` 預設就是運算式本身的文字，只有在人話比較好懂的時候才寫（I2、A）。

### 判定細節也是推導的

輸出括號裡那句話從運算式的**形狀**來：比較報兩邊的值、量詞點名誰不成立、
`consistent` 報帳上幾筆。沒有一行程式碼知道 I1 在講願望數。
代價是文字跟手寫版不完全一樣（`(dead: rival)` 變成 `(fails for: rival)`），
換到的是加一條不變量不必再寫一份說明。
