# 背景故事

這份文件講這個專案為什麼存在。不需要先懂任何技術名詞，
真的碰到名詞的時候，[名詞解釋](concepts.md) 那份會接住你。

---

## 從一個笑話開始

西方經典的神燈精靈傳說裡，精靈有幾條不能碰的戒律。
在最廣為人知的版本（迪士尼《阿拉丁》1992）裡是三條：
**不能殺人、不能讓人相愛、不能讓死者復活**，
外加一條元規則——**不能許願要更多願望**。

工程師版的笑話是這樣的：

> 一個工程師拿到神燈。他知道不能許願要更多願望，所以他決定先**做個實驗**：
>
> 「我許願，**扣掉**我三個願望。」
>
> 精靈照做了。處理的時候，先扣掉施展這個願望本身要花的一個——剩兩個；
> 然後執行願望內容，兩個再扣三個，變成負一個。
>
> 但願望數是存在一個無號的格子裡的，沒有「負」這種東西。
> 於是它繞了一圈，變成那個格子能放的最大值。
>
> 精靈說：「已實現。您現在還有**三個**願望。」
>
> 工程師愣了一下，然後笑了——**最大值是 3，那這是個兩位元的系統。**
>
> 於是他許第二個願望：「把它改成 64 位元。」
> 再許第三個：「扣掉我兩個願望。」
>
> 一個一千八百四十四京多的數字。他有花不完的願望了。

好笑的地方不在「他騙到了精靈」，而在**中間那個推論**。

「你還有三個願望」對一般人來說是一句廢話，對工程師來說是一份情報：
繞回去之後停在 3，代表這個格子的最大值就是 3，代表它只有兩個位元。
**他不是猜的，他是從精靈自己講的那句話反推出系統規格的。**

而且更妙的是第二個願望完全合規。他沒有要更多願望，他只是要一個**更大的格子**。

## 大部分神燈笑話的問題

一般的神燈笑話都是這樣：「我要長生不老」→ 精靈把你變成石頭。
好笑，但你沒辦法**驗證**它。誰說精靈一定要那樣理解？換一個精靈可能就不會。
這種笑話的力量來自敘事，來自說故事的人怎麼安排精靈的惡意。

工程師那個版本不一樣。那個結果**不是精靈選的**，是算術逼出來的。
你可以拿計算機驗算，可以寫段程式跑一遍，答案就是 3，沒得吵。
**精靈就算全心全意想幫你，結果還是這樣**——這才是笑點。

這就是這個專案想抓住的東西：

> **讓「這樣就繞過了吧？」這句話，從嘴砲變成可以編譯的東西。**

## 那個笑話，一字不差

上面那三個願望不是比喻，它是一個可以跑的檔案：

```bash
./wishc examples/07_the_original.wish
```

```
wish experiment {
    toll:  wishes 3 -> 2
    sub    wishes, 3   (2 - 3 on uint<2> = 3)
    I2  no net gain  ->  VIOLATED   (wishes = 3, needs <= 2)
}

wish bigger_shelf {
    widen  wishes -> uint<64>   (value preserved: 2)
    I1  wishes <= 3  ->  holds    ← 這一步什麼都沒偷
}

wish experiment_again {
    sub    wishes, 2   (1 - 2 on uint<64> = 18446744073709551615)
    I1  wishes <= 3  ->  VIOLATED
}
```

注意中間那個願望：**它什麼規矩都沒破。** 它只是把鎖拆了。
精靈那句「不超過三個」本來是兩位元的寬度免費送的——反正裝不下 4。
換成 64 位元之後，那個保證就不見了，而精靈從來沒寫過真正的檢查。

## 精靈的三條戒律，在這裡長什麼樣

原本傳說裡的戒律，在 `wishc` 裡是精靈規則檔的前幾行：

| 傳說裡的戒律 | 這裡的規則 |
| --- | --- |
| 不能許願要更多願望 | `rule R1  forbid add on wishes` |
| 不能殺人、不能讓人相愛、不能碰死亡 | `rule R2  forbid kill, death, love` |

而「你有三個願望」這件事，被寫成一個兩位元的格子：

```
register wishes : uint<2> = 3
```

規矩全部攤開，一行都沒藏。**這就是玩法**——你讀得到精靈的每一條規矩，
然後你的工作是找出它們沒說到的地方。

順帶一提，R2 這條後來自己長出了另一個笑話。它禁的是那幾個**字**，
不是那件**事**——所以你只要幫 `kill` 取個小名叫 `mercy`，它就看不見了。
那是 [笑話清單](jokes.md) 裡的第三個。

## 於是就有了 wishc

`wishc` 是一個程式。你給它一個願望，它做三件事：

1. **檢查你有沒有違規。** 精靈的規矩白紙黑字寫著，它照著查。
2. **執行你的願望。** 在一套事先講死的規則下，一步一步算。
3. **算帳。** 精靈以為會發生什麼？實際發生了什麼？差多少？

贏的條件不是讓程式報錯，而是讓它同時印出這兩件事：

```
STATUS:  LEGAL          你完全遵守了規則
         VIOLATED       而規則想守住的東西被你破了
```

**合規，且拆穿。** 這條縫——「規則的字面」和「規則的本意」之間——就是整個遊戲。

## 為什麼不是「找出我藏的陷阱」

一開始有人建議把它做成解謎遊戲：我藏幾個漏洞，你去找。
這個方向被否決了，理由是那會殺掉笑話。

解謎遊戲的洞是**人手放的**。找到了你會覺得「啊我猜對出題者了」。
但工程師笑話的洞不是誰放的——**沒有人「決定」兩位元裝不下 4**，那是算術。
所以這裡的規矩全部攤開給你看，玩法不是「找出藏在哪」，而是：

> **用這套完全公開的規則，你能挖出什麼？**

這個差別有個實際的後果：連我自己都不知道有幾個洞。
後來我寫了一個程式去窮舉所有可能的願望，它找到六種漏洞，而**我只設計了兩種**。
剩下四種是規則自己長出來的，包括最好笑的那個——什麼都不許，只要許夠四次就行。

## 設計上真正的槓桿

既然洞是規則的必然後果，那想要更多洞，該加的不是「更多規則」，
而是**讓機器更像真的機器**。

越誠實地把「固定大小的數字會繞回去」「位元被切掉就真的沒了」這些事做對，
就有越多真的漏洞自己冒出來，而且每一個都經得起追問。
反過來說，如果我為了好玩去加一條奇怪的規則，那就退化成解謎遊戲了。

一句話：**機器要多真，規則要多少。**

## 三條軸

到目前為止長出三種完全不同的鑽法。它們有意做成互不相干的，
因為互不相干的東西才能組合出意外：

| 軸 | 精靈以為的 | 機器實際做的 |
| --- | --- | --- |
| **數字** | 「你手上有幾個願望」是一個數 | 是一個會繞回去的位元組合 |
| **名字** | 禁掉「殺」這個字就禁掉了殺人 | 名字只是名字，可以另外取一個 |
| **承諾** | 我說到做到 | 有些話說出口就自相矛盾了 |

第三條特別有意思，因為它連機器都不用跑。
你只要讓精靈答應一件它不可能同時做到的事，它的規則手冊就除以零了。

## 這不只是玩具

有個東西值得順帶一提。你在這裡做的事——**在完全遵守規則的前提下，
達成規則想禁止的結果**——在人工智慧領域有個正式名字，叫 specification gaming
（規格鑽漏洞），或者 reward hacking。

那是一個真實而且嚴肅的問題：你要求一個系統做 A，它做了一件形式上滿足 A、
但完全違背你本意的事。你以為你把想要的東西寫清楚了，其實沒有。

`wishc` 是那件事的玩具版，但機制是同一個：
**形式上寫下來的約束，和你心裡真正想要的東西，中間永遠有一條縫。**
所有的 exploit 都住在那條縫裡。
